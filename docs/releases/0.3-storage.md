# Release `0.3-storage` — publicada (2026-09-01, após `v0.2-userspace`)

**Marco:** Plano Mestre §7 — driver de bloco, sistema de arquivos com integridade sob corte de
energia, VFS com namespaces; "testes de corrupção e corte de energia" como critério.
**Estado:** publicada. Gate F3 atendido desde 2026-08-30; entre a conclusão e a publicação o
subsistema ganhou ainda NVMe (MSI-X + pedidos em voo) rodando a MESMA pilha sem mudanças.

## Critérios do gate F3 — atendidos (testes no boot a cada push)

- Criar, ler, alterar e remover arquivos sobre VirtIO block (`user_fs`, shell `ls/cat/escreve/
  remove`); reiniciar preserva dados (`boot.count`; cenário `storage` com 2 boots).
- Driver de armazenamento pode falhar sem corromper o kernel (`user_block_crash`; cenários
  `fault`).
- Desligamentos abruptos simulados: cenário `powercut` (SIGKILL no QEMU durante escritas,
  múltiplas execuções) + testes de host do NexoFS com **corte injetado em cada escrita** e
  imagens corrompidas no parser.

## Conteúdo do marco (já em `main`)

`services/blockdev` (VirtIO-block, MSI-X, fila assíncrona), `libraries/nexofs` (NexoFS v0:
commits atômicos por setor — ADR-0016), `services/fs` (protocolo tipado `nexo.fs` + cache),
`services/vfs` (namespaces por instância: /disk, /boot ro, /tmp), `services/espfs` +
`libraries/fat` (ESP FAT32 somente-leitura), `tools/nexo-disk`. Extra pós-gate: `nvmedev`
(NVMe em ring 3) com a pilha inteira intacta — substituibilidade por protocolo.

## Limitações conhecidas

Sem quotas (ENOSPC é gracioso — provado em campo); um cliente por servidor `fs`
(multiplexação é papel do vfs); sem criptografia de disco (Fase 8, decisão de cripto);
threat model §6.
